# 운영 콘솔과 추론 처리의 선택 이유

## 문제

사용자 웹 안의 신고 화면만으로 회원 상태와 복수 신고, 운영 조치 이력을 함께 다루기 어려웠습니다. 로컬 모델은 요청별 연결 생성과 모델 재적재 비용이 있고, 동시 요청이 과도하면 개별 응답도 늦어질 수 있습니다.

## 결정과 이유

운영 사이트를 독립 Angular 앱으로 두어 사용자의 창작 화면과 배포 단위를 나눴습니다. 권한은 기존 서버 설정을 사용하고 각 API에서 다시 검증하여, UI 접근 여부만으로 데이터를 보호하지 않습니다.

`develop` 통합 시 기존 `prod`가 단일 출처만 허용해 독립 콘솔을 배포할 수 없는 충돌을 확인했습니다. 웹·콘솔 각각의 HTTPS 출처 하나를 검증하고 두 개만 허용하도록 확장했습니다. 개발 자격 증명 거부, 고정 JWT, 신뢰 프록시와 API 문서 차단은 보존했습니다.

운영 조치는 빈도가 상대적으로 낮으므로 공통 DB 잠금 행으로 순서를 보장했습니다. 복잡한 분산 작업 큐를 추가하기 전에 단건·일괄·회원 조치가 같은 충돌 규칙을 따르게 하는 선택입니다. 변경·알림·감사를 같은 트랜잭션으로 묶어 처리 일부만 남지 않게 했습니다. 처리량이 커지면 대상별 잠금과 독립 작업 큐를 검토할 수 있습니다.

추론은 모델 변경이나 필수 컨텍스트 축소 대신 연결 재사용, 모델 상주와 선택적 예열, 제한된 동시 실행을 적용했습니다. 구조화 출력은 모델에 스키마를 전달하고 실패를 명시합니다. 속도를 위해 손상된 JSON을 정상 결과로 수선하거나 Continuity를 생략하지 않습니다. 모델의 추론 출력은 설정으로 켤 수 있게 두었습니다.

실제 성능은 하드웨어와 컨텍스트 크기에 크게 의존하므로 짧은 프롬프트 수치를 장편 성능으로 일반화하지 않습니다. 브라우저 자동화의 안전 검사 중단도 테스트 통과로 표시하지 않고, 사용자의 제한 수용 지시와 함께 기록했습니다.

## 다시 검토할 조건

운영 조치 잠금 대기가 커지거나 여러 FastAPI worker·GPU를 사용하면 실제 부하와 전체 동시성을 기준으로 재설계합니다. 외부 운영을 시작하기 전에는 브라우저·접근 제한·감사 보존과 긴 컨텍스트 성능을 확인해야 합니다.
